## 2. Архитектурная парадигма: Clean Architecture & SOLID

Проект спроектирован по принципам **Чистой Архитектуры (Clean Architecture)** Роберта Мартина. Код разделен на независимые слои с направлением зависимостей строго снаружи внутрь:

```
[Presentation / API Layer] (Next.js App Router, React Components)
             │
             ▼
[Application Layer] (Use Cases: ProcessChatMessage, HandleTelegramUpdate, etc.)
             │
             ▼
[Domain Layer] (Entities: Message, Session, Soul, Provider; Core Interfaces)
             ▲
             │
[Infrastructure Layer] (Adapters: GroqLlmAdapter, TelegramBotAdapter, Repositories)
```

### 1. Доменный слой (`src/core/domain`)
- **Полная изоляция**: не зависит ни от каких внешних библиотек, фреймворков и баз данных.
- **Сущности (`entities/`)**:
  - `MessageEntity`: модель сообщения с автоматическим расчетом токенов по эвристике для латиницы и кириллицы (предотвращает выход за пределы контекстного окна).
  - `SessionEntity`: управление состоянием диалога с динамической компактизацией (sliding window context pruning), сохраняющей системный промпт и последние реплики при превышении лимита токенов.
  - `SoulEntity`: представление личности и системных инструкций бота, загруженных из спецификации `SOUL.md`.
  - `ProviderEntity`: типизированные модели провайдеров и статуса сетевой связности.
- **Контракты и интерфейсы (`interfaces/`)**:
  - `ILlmProvider`: абстракция над LLM-движком (генерация ответов, расчет затрат).
  - `IMessengerAdapter`: контракт мессенджера (отправка сообщений, вебхуки, поллинг).
  - `ISessionRepository`: контракт хранилища сессий (in-memory, Redis, PostgreSQL).
  - `ISoulRepository`: контракт загрузки и обновления файла личности.
  - `IProxyService`: абстракция проверки связности и проксирования.

### 2. Прикладной слой (`src/core/application/use-cases`)
Содержит чистую бизнес-логику системы, управляющую сценариями использования:
- `ProcessChatMessageUseCase`: извлекает контекст сессии, валидирует размер буфера, подмешивает системные инструкции из `SOUL.md`, вызывает LLM-провайдер и сохраняет ответ.
- `HandleTelegramUpdateUseCase`: точка входа для Telegram (вебхуки или long-polling). Проверяет пользователя по белому списку `TELEGRAM_ALLOWED_USERS`, парсит команды (`/start`, `/status`, `/help`, `/reset`), передает диалог в `ProcessChatMessageUseCase` и отправляет ответ в чат.
- `ManageSoulUseCase`: чтение, парсинг и валидация структуры `SOUL.md`.
- `TestConnectivityUseCase`: замер задержек (RTT) и проверка доступности внешних узлов (Telegram API, Groq Cloud, определение выходного IP).
- `GetGatewayStatusUseCase`: сбор диагностических метрик шлюза (аптайм, количество сессий, активные провайдеры).

### 3. Инфраструктурный слой (`src/infrastructure`)
Реализует доменные интерфейсы через конкретные технологии:
- `GroqLlmAdapter`: клиент к REST API Groq Cloud с поддержкой стриминга и fallback на различные модели семейства Qwen и LLaMA.
- `TelegramBotAdapter`: интеграция с Telegram Bot API с поддержкой как облачного вебхука, так и локального long-polling через `SOCKS5`-туннель.
- `InMemorySessionRepository`: потокобезопасное in-memory хранилище сессий со сборщиком устаревших контекстов.
- `FileSoulRepository`: загрузчик `SOUL.md` с диска с безопасным fallback на дефолтную техническую личность.
- `Container (src/infrastructure/container.ts)`: легковесный контейнер внедрения зависимостей (Dependency Injection / Inversion of Control), связывающий конкретные адаптеры с юзкейсами при старте приложения.

## 3. Механизм обхода сетевых ограничений из РФ (No-VPN Architecture)

Для бесперебойной работы из российских сетей без необходимости поднимать глобальный VPN на хост-машине реализована двухуровневая стратегия:

### Сценарий 1: Облачный продакшен (Vercel Serverless)
- Трафик от серверов Telegram доставляется на эндпоинт `POST /api/telegram/webhook`.
- Так как серверы Vercel располагаются в международных дата-центрах (EU/US), вебхуки принимаются напрямую без блокировок со стороны РКН и провайдеров.
- Ответы к Telegram Bot API и запросы к LLM выполняются из зарубежной зоны с минимальными сетевыми задержками.

### Сценарий 2: Локальная разработка и автономный сервер (Docker / Polling Worker)
- Для локального запуска доступен фоновый процесс `npm run bot:polling` (`scripts/run-local-polling.ts`).
- Реализован универсальный клиент `proxyFetch` (`src/infrastructure/services/proxy-http-client.ts`), поддерживающий как SOCKS5 (`socks5://...`), так и HTTP CONNECT (`http://user:pass@host:port`) проксирование.
- Все внешние обращения (как к Telegram Bot API, так и к AI-провайдерам Groq, OpenRouter) автоматически маршрутизируются через настроенный прикладной прокси-агент.
- При этом системный трафик операционной системы хоста, локальные DNS-таблицы, сетевые адаптеры и локальные веб-сервисы остаются полностью нетронутыми.

## 4. Концепция SOUL.md: спецификация личности и безопасности

Файл `SOUL.md` описывает системное поведение ассистента в формате структурированного Markdown:
1. **Директивы роли (Role & Scope)**: жесткая фиксация ассистента в рамках задач шлюза и разработки.
2. **Безопасность (Security Guardrails)**: запрет на выполнение разрушительных команд, защита от Prompt Injection, экранирование конфиденциальных токенов окружения.
3. **Формат ответов**: лаконичный инженерный стиль без лишних вводных слов, приоритет русского и английского языков.
4. **Контекстный бюджет**: ограничение sliding window до 3500 токенов, что гарантирует стабильную работу моделей с любым размером контекста.

## 5. Порядок обработки запроса (Sequence Flow)

```
[Пользователь] 
      │ 1. Сообщение в Telegram
      ▼
[Telegram Bot API] 
      │ 2. Webhook HTTP POST
      ▼
[/api/telegram/webhook (Next.js Route Handler)]
      │ 3. Передача в HandleTelegramUpdateUseCase
      ▼
[HandleTelegramUpdateUseCase]
      │ 4. Проверка прав (whitelist)
      │ 5. Вызов ProcessChatMessageUseCase
      ▼
[ProcessChatMessageUseCase]
      │ 6. Получение/создание SessionEntity
      │ 7. Чтение системных инструкций из SOUL.md
      │ 8. Оптимизация контекста (компактизация)
      │ 9. Запрос к GroqLlmAdapter (ILlmProvider)
      ▼
[Groq Cloud (Qwen / LLaMA)]
      │ 10. Токены ответа (< 200 мс)
      ▼
[ProcessChatMessageUseCase]
      │ 11. Обновление SessionEntity
      ▼
[TelegramBotAdapter]
      │ 12. sendMessage в чат пользователя
      ▼
[Пользователь получает ответ]
```
